Both gaps were verified absent first: `grep -ri "voting rights"` and `grep -ri "elects majority preferred winners"` each returned nothing repo-wide.

- [At-large elections and the Voting Rights Act](https://masiarek.github.io/star-voting-library/02_STAR_Bloc/01_Learn/at_large_and_the_vra.html) — the sweep as vote dilution. **Correction carried in print:** at-large bloc voting was *not* "banned in the Voting Rights Act" as starvoting.org says; §2 names no methods, and at-large elections are legal and everywhere. What §2 does is make one actionable where it dilutes, on the 1982 results test, screened by the three *Gingles* preconditions (478 U.S. 30 (1986)). Those three read as the majority-sweep page in legal vocabulary.
- [The Bloc STAR ballot and the official definitions](https://masiarek.github.io/star-voting-library/02_STAR_Bloc/01_Learn/bloc_ballot_language.html) — the published instructions line by line, plus the naming rules.

**The find worth remembering from that second page.** `starvoting.org/technical_specifications` 301s to a **scanned PDF with no text layer** (v1.3, published 2024-12-20), so nobody reads it and the wordings have drifted. Text pulled out of the font-encoded streams directly (subset font, uniform **+29** code offset — `chr(code + 29)` decodes it; the extraction script pattern is in that session's scratchpad but is three lines of `zlib` + regex over `BT…ET` blocks). What it says:

| | technical specifications §3.d | the circulated paper-ballot text |
|---|---|---|
| who wins a seat | "**the finalist** preferred by the most voters wins" | "**the candidate** with the most votes is elected" |
| the ballot goes to | "your vote" | "your **full** vote" |
| the winner count | above the race (§3.c) | folded into the first instruction |

The circulated clause is the one that invites reading stars as votes and concluding the top scorer wins — which Bloc STAR does not guarantee. §3.e licenses paraphrase "with the meaning unchanged", so neither is off-spec, but that row is where the meaning arguably *is* changed. Also: §3.a makes printing the instructions **mandatory**, and §2.c's terse "an additional Automatic Runoff round conducted for each seat" is correct rather than sloppy — because removal leaves every remaining score untouched, only the runoff genuinely repeats.

**One mistake worth not repeating.** The GitHub **contents API PUT is a whole-file overwrite**, and passing the current blob `sha` only proves nobody wrote *since you read it*. A commit built from a scratchpad copy silently reverted a correction that had landed on the branch in between (restored in `745a4a3`, ~10 minutes wrong on an unmerged branch). Always re-`GET` the remote file, patch that string, and PUT it back.

## The fourth thread — `regen_all` on a clean master is now a no-op

Found while adding BV1835 and deliberately kept out of that commit. A clean detached worktree at `origin/master`, nothing edited, reported **seven files modified** after a single `regen_all.py` run. Two unrelated causes wearing one symptom, so the working note that recorded it ([`39cedee8`](https://github.com/masiarek/star-voting-library/commit/39cedee8)) is now deleted and the rule lives in `CONTRIBUTING.md` instead.

**Row-order churn.** [`efe7c370`](https://github.com/masiarek/star-voting-library/commit/efe7c370) "Park the flat-scores tie set" moved the set into `01_STAR/09_Parked/` and rewrote the paths *inside* `divergence.csv` in place without re-sorting. The builder sorts by `(bucket, file)`, so those eight rows sat under their **pre-move** sort key — `03_Criteria/Flat_scores_ties` sorts before `03_Criteria/equal_and_opposite` because uppercase `F` (70) precedes lowercase `e` (101). Fixed independently in [`e89dc80d`](https://github.com/masiarek/star-voting-library/commit/e89dc80d).

**Line endings — and the working note had the direction backwards.** The committed CSVs are **LF**; the *generators* were writing **CRLF**, because Python's `csv` module defaults to RFC 4180. That inverts both fixes the note proposed: "make the writers emit CRLF to match what is committed" would have meant reverting `.gitattributes` and rewriting every stored blob, and the `.gitattributes` rule it suggested adding was already there — `*.csv text eol=lf`, committed 2026-06-20. The real cause was smaller than either: four builders were missing the `lineterminator="\n"` that three sibling tools under `tools_adam/` already pass, with that exact comment. [`6f3588f5`](https://github.com/masiarek/star-voting-library/commit/6f3588f5) gives it to `build_catalog.py` (races + elections), `build_bv_registry.py`, `build_paradox_index.py` and `build_divergence_index.py`.

Verified twice on a fresh detached worktree at master: `regen_all` touches nothing, `git status` comes back clean, and no CRLF warning. Closed out in [`c5b8f0b1`](https://github.com/masiarek/star-voting-library/commit/c5b8f0b1).

**One diagnostic trap worth carrying to the new machine.** While testing, the main checkout kept reporting those five CSVs as ` M` *after* they were already byte-identical to the index — a stale stat-cache entry, not drift. `git diff` was empty throughout and `git hash-object` matched; `git checkout --` on the files clears it. When `git status` and `git diff` disagree about a generated file, believe `git diff`.
